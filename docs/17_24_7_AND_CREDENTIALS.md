# 17. 24/7 自律実行とクレデンシャル主権

> 決定事項の保存場所。2026-06-22 のセッションで詰めた「ユーザーがマシンを閉じても 24/7 で動かす方法」と、その堀の正確な定義。

## 0. 出発点の問い

> 「ユーザーに課金させるために、こちらがホストしてユーザーがパソコンを閉じても 24/7 にできる方法はあるか?」

直感的には「クラウドで hub を常駐させればよい」。だが browser-control(本人ログインでの UI 操作)を含めた瞬間、これは**構造的な壁**にぶつかる。コードにも既にこの区別が埋まっている(`settings.html` の `managed hub` vs `self-host` バッジ)。

## 1. 24/7 を実現する「扉は3つしかない」定理

ログイン必須サービスを**不在中も** 24/7 でやるには、本人として振る舞える **bearer 資格情報が「どこかに・継続的に」存在せねばならない**。これは論理的に3つの扉に閉じる:

| 扉 | 資格情報はどこ | 結果 | 例 |
|---|---|---|---|
| **A** | 第三者(ホスター)のクラウド | 24/7 ○ / 保管リスク | Zapier・Browserbase・Skyvern・RPA |
| **B** | 持たない(認証時に人を呼ぶ) | 24/7 ✗(無人にならない) | OpenAI Operator・ChatGPT agent |
| **C** | ユーザー自身のマシン | 24/7 ○ / 第三者保管なし | **エッジ箱・self-host(神龍)** |

第四の扉は無い。「不在中に本人として動く」=「本人の鍵がその間どこかで使える状態」だから。

## 2. 他社はどう 24/7 しているか(5類型)

| # | 誰 | やり方 | 飲んでいる毒 | 扉 |
|---|---|---|---|---|
| 1 | Zapier / Make / n8n cloud | OAuth トークンを預かりサーバ側で 24/7。ブラウザを触らない | API が無いサービスは不可。commodity | A |
| 2 | Browserbase / Skyvern / Browser Use | クラウドのブラウザ農場。1回ログイン→cookie/token/localStorage/MFA-trust を "context" に保存→以降クラウドで再生 | セッション期限切れで再ログイン(人が要る)。クラウド IP の bot 検知を residential proxy + stealth で回避する軍拡。実質ユーザーの session を保持 | A |
| 3 | OpenAI Operator / ChatGPT agent | クラウドブラウザだが、ログインの瞬間に人へ操作を返す("Take over browser"・スクショ停止)。パスワードは保存しない | 真の無人 24/7 ではない。認証の瞬間に人が必要 | B |
| 4 | RPA(UiPath / Automation Anywhere) | 専用 VM + 専用サービスアカウント(独自 ID・IT が MFA 免除で発行)。会社所有インフラで 24/7 | 企業限定。IT がロボット用 ID を作る前提 | A |
| 5 | n8n self-host / Home Assistant / **神龍の箱案** | ユーザー自身の常駐ハードで動かす | 24/7 をユーザー側に押し付ける(=堀は保つ) | C |

**結論: 全社が同じ断層で割れている。** クラウドでホストする勢(#2)はセッション状態を保持してセキュリティ/ToS/anti-bot のコストを飲む。保持を拒む勢(#3)は人を呼ぶ。唯一の逃げ道が資格情報をユーザーのマシンに置いたまま(#4 企業 / #5 神龍)。

## 3. 「資格情報を保持するか否か」ではない — 「誰が・どこで・どの種類か」

**エッジ箱も資格情報を保持している。** 24/7 なら誰かが持つしかない。違いは保持の有無ではなく**保管者・場所・種類**:

| 種類(丁寧 → 危険) | 何 | 誰が持つ | クラウド保管の可否 |
|---|---|---|---|
| OAuth トークン | 範囲限定・取消可・サービス公認の委任鍵 | Zapier(クラウド) | ○ 漏れても範囲限定・取消可 |
| 専用サービスアカウント | ロボット用に IT が発行した別 ID | RPA(企業VM) | △ 企業統制下 |
| **bearer フルセッション** | 本人の cookie/MFA-trust 丸ごと・本人と区別不能 | Browserbase(クラウド) | ✗ 本人のコピーになる |
| パスワード保管 | 最悪 | — | ✗ |

### エッジ箱の堀の正確な定義

> 堀は「資格情報を**保持しない**」ではない。「第三者(サービス提供者である自分を含む)に**渡さない**・マシンの外に**出さない**」だ。

鍵は持つが、ユーザーが・自分のハードで・誰のコピーも作らずに持つ。神龍は既にこれをコードで扱っている(`vault.mjs` の `set_credential`/`get_credential` = 保存はするが値は二度と返さない・Mac は Keychain・MCP は presence のみ返す)。

## 4. 設計線: scoped はクラウド可・bearer は箱必須

この精密化から、「エッジ箱 + BYO-key hub」の役割分担が**一本の設計原則**として落ちる:

- **範囲限定で取消可な資格情報(OAuth トークン・ユーザーの Anthropic API キー)** → クラウドの managed hub に置いてよい(漏れても範囲限定・取り消せる)。これが API フローのオンランプ。
- **bearer フルセッション(本人ログイン済みブラウザ)** → 絶対にマシンの外に出さない = **エッジ箱必須**。

→「危険な鍵だけ箱に閉じ込め、安全な鍵はクラウドで利便性を出す」。

## 5. ポジショニング耐久テスト(whitespace)

「エッジ箱 + BYO-key hub」を耐久テストした結果:

- **OpenAI / Zapier / Browserbase / n8n に対しては 🟢 構造的**。追随には三重自傷が必要 — (1)トークン従量収益の放棄(BYO-key)、(2)クラウドで bearer 資格情報を保持する責任 or 無人の断念、(3)消費者ハード/常駐 UX への転換。
- **だが Anthropic 自身に対しては 🔴**。Claude for Chrome は既に本人ブラウザで動き(資格情報主権を満たす)、Claude Code は既にローカル MCP-native、compute は自社サブスクで包める(BYO-key 不要)。**三重自傷が無い** → この空白の屋根を、土台にしている Anthropic 自身が握っている。
- **買い手は狭い(🟡)**。箱を買う($100–700)+設定する技術力+常時電源を越える層 = Home Assistant 的ホビイストに限られる。一般人は「Operator をたまに叩く」で満足閾値に達する。
- **無人信頼性が技術的に脆い**。browser-control は UI 変更/bot 検知/セッション期限で壊れ、無人ほど「気づいたら3日壊れてた」。決定論(API)に焼けない操作は無人運用の信頼性が低い = 価値提案の根を腐らせる moat killer。

**判定: エッジ箱単体は 🟢 ではなく 🟡。** 防御可能だが、屋根を Anthropic が握り、買い手が狭く、無人信頼性が脆い。撤退ではないが「勝てる空白」と断言する前に検証が要る。

## 6. より鋭い形: credential-aware routing

「ユーザーにどの扉か選ばせる」を**生で出すのは UX 毒**(決定負担・positioning 希釈)。正しい組み替え = **資格情報の種類から自動で扉を振り分け、本物の分岐だけ聞く**:

- OAuth / API キー → 扉A(クラウド hub)に自動。聞かない。
- bearer セッション要 → ここだけ聞く:「**常駐箱で 24/7 回す? それとも都度ログインを引き受ける(箱不要)?**」(= 扉C vs 扉B、一般人にも分かる「利便性 vs ハード」のトレードオフ)。

各巨人は**扉を1つしか持たない**(Zapier/Browserbase=常にA、Operator=常にB)。**3つの扉を持って資格情報の機微で振り分ける**システムは存在しない — 扉C を持つには本人のエッジマシンで動く必要があるから。よって credential-aware routing は**エッジ箱単体より鋭い堀**(静的な「箱がある」→ 動的な「機微で扉を選ぶ・全扉を持つ者だけ可能」)。

ただし **🟡 の需要は動かない**。routing は堀を*使いやすく*する feature であって、新しい demand source ではない。

### 実装(lazy・既存パターンに乗る)

`plan_flow` は既に discover-first + `clarify`(質問+選択肢を返す)を持つ。やること = discover で各ステップの資格情報種別を判定し、bearer が要るステップでだけ `clarify` を1つ出す(箱=24/7 / 都度ログイン)。ルーティングは model/cost routing の隣に "custody" を1本足すだけ。新サーフェス不要。

## 7. 次にやる検証(コード不要 / 最小)

1. **需要(Wizard of Oz)**: 箱を作る前に、技術好きだが時間ない個人 5–10 人に「あなたの定期 web 作業を、あなたのマシンで動く神龍が 24/7 やります」を提示し、Mom Test で (a)いくら払うか (b)箱常駐を受け入れるか (c)どの反復作業か を聞く。1週間。
2. **無人信頼性**: 実 browser-control フロー1本(例: 毎日ある site にログインしてデータ取得)を自分の箱で2週間無人運用し、何回壊れたかを数える。週1以上壊れるなら「24/7 無人」は商品にならない = 価値提案を作り直し。
3. **Anthropic 屋根リスク**: 検証不能(彼らの roadmap 次第)。「Claude desktop の常駐機能発表」等を監視シグナルにする。
